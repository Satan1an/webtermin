## Пре-релизный аудит (v0.1.0, 2026-05-16)

Перед первым публичным тегом весь код был вручную проверен на типичные классы рисков серверного ПО, поверх запущена автоматика.

### Инструменты

- **`govulncheck ./...`** — чисто против опубликованной базы уязвимостей после бампа toolchain до `go 1.25.10` (фиксит 14 stdlib CVE в `crypto/tls`, `crypto/x509`, `net`, `net/http`, `net/url`, `os`).
- **Grep-аудиты**:
  - Все `exec.Command` / `exec.CommandContext` используют argv-слайсы, ни одного `sh -c`.
  - Все SQL-запросы используют `?`-плейсхолдеры, никакой строковой конкатенации.
  - Нет захардкоженных учётных данных, API-ключей или токенов.
  - Все файловые маски выставлены осознанно (`0o700` для секретных директорий, `0o600` для cert/key + `authorized_keys`).

### Ключевые выводы ручного review

| Зона | Вердикт |
| --- | --- |
| Аутентификация | Argon2id `(64 МиБ, t=2, p=2)` соответствует OWASP 2024-baseline; при промахе по логину всё равно прогоняется dummy-hash для смягчения timing-атак. |
| Session cookies | `HttpOnly` + `Secure` + `SameSite=Strict` и на set, и на clear. ID 256-битные случайные. |
| CSRF | На каждом изменяющем запросе обязателен заголовок `X-CSRF-Token`; сравнение constant-time. |
| Lockout | Per-IP счётчик неудачных входов с настраиваемым порогом и cooldown; на 429 возвращается `Retry-After`. |
| TLS | Минимум TLS 1.2, self-signed P-256 cert автогенерится при первом запуске, заменяется через конфиг. |
| Security headers | HSTS 2y, строгий CSP, X-Frame-Options DENY, nosniff, no-referrer, минималистичный Permissions-Policy. |
| Выполнение команд | Все вызывающие (`chpasswd`, `useradd`, `userdel`, `journalctl`, `/bin/bash`) передают аргументы через argv. Ввод валидируется allowlist-регексами перед exec. |
| WebSocket | Same-origin проверяется через `CheckOrigin`; missing/foreign Origin → upgrade отклоняется. |
| Безопасность путей | Каждая файловая операция в `internal/files/` проходит `SafePath` (абсолютный + cleaned; запрещает `..`). |
| Аудит-лог | Каждое изменяющее действие записывается в SQLite: пользователь, IP, действие, цель, результат. |

### Осознанные by-design трейд-оффы

- Процесс панели работает от **root** — нужно для управления системными пользователями, сервисами и произвольными файлами хоста. Митигируется Argon2id + 2FA + audit log + allowlist действий.
- Docker compose файл запускает `privileged: true` с bind-mount'ами хостовых `/etc`, `/home` и `/run/dbus` — нужно чтобы управлять хостом *из* контейнера.
- CSP разрешает `'unsafe-eval'` (Monaco worker'ы) и `'unsafe-inline'` стили (Tailwind atomic CSS).
- Любой пользователь панели сейчас admin; per-user RBAC — в roadmap.

Они задокументированы здесь, чтобы пользователи могли принять информированное решение о деплое — а не потому что считаются приемлемыми риски для любой модели угроз.

## Где можно запускать webtermin

Честная оценка состояния на v0.1.0:

### ✅ Можно прямо сейчас

- **Home-lab / NAS за роутером** — нет публичного доступа извне, доверенная сеть.
- **Сервер за Tailscale / WireGuard** — :8443 видят только клиенты с ключами.
- **Локальный dev/test** — биндинг на `127.0.0.1`, никаких публичных портов.
- **Внутренний корпоративный VPN** — если уровень доверия как для SSH-bastion.

### ⚠ Можно с осторожностью

- **VPS с публичным IP** — только если:
  - Reverse proxy (Caddy/nginx) с IP-whitelist'ом, **либо** Cloudflare Access / Cloudflare Tunnel поверх
  - **Обязательно** 2FA для всех аккаунтов
  - Сложный пароль (≥ 20 символов)
  - fail2ban на 8443
  - Регулярно (хотя бы раз в неделю) смотрите audit-лог

### ❌ Нельзя

- **Production-сервер с конфиденциальными данными клиентов** — нет внешнего аудита, нет CVE-response процесса, нет SLA. Дождитесь v1.0.
- **Голый порт 8443 в интернет без proxy/firewall** — даже с 2FA, неизвестный 0day всё равно опаснее лишнего слоя защиты.
- **Сервер где вы не контролируете физический/гипервизор-уровень** — root в контейнере панели = root на хосте.

## Что в scope

- Обход аутентификации или сессии (любой путь, который доходит до authed-эндпоинта без валидной сессии).
- Обход авторизации (например, один пользователь читает audit-данные другого или подделывает действия от чужого имени).
- Argument-injection или path-traversal в любом модуле — даже если приводит только к неожиданной ошибке, об этом стоит сообщить.
- Неправильные настройки TLS, CSP или cookie, ослабляющие дефолты.
- Container-escape в задокументированной Docker-конфигурации (помимо тех привилегий, которые `privileged: true` явно даёт).

## Что НЕ в scope

- То, что `docker-compose.yml` запускает контейнер `privileged: true` и bind-mount'ит хостовые пути — это by design (панель управляет хостом).
- То, что процесс панели работает от `root` — нужно для управления systemd / пользователями / файлами. Per-user RBAC в roadmap.
- Репорты против тестового или example-кода в ветках, отличных от `main`.

## Таймлайн disclosure

По умолчанию: coordinated disclosure через 90 дней после первоначального репорта или после релиза фикса — что наступит раньше. С удовольствием упомянем вас в release notes, если хотите.
